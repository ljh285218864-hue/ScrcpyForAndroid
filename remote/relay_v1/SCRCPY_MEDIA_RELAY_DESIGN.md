# ScreenSync Beta4 — 保留 ADB+scrcpy 的无 VPN 异地方案

## 用户确定的目标

- **屏幕数据来源继续用现有 ADB + scrcpy**，不改成 Android MediaProjection。
- **两台手机的网络都向用户自己的日本服务器主动建立加密连接**，不要求同一 Wi-Fi、固定局域网 IP 或 Android 系统 VPN。A 可以看 B，B 也可以看 A。
- **不添加前台常驻通知服务**。但不隐藏 Android 的系统安全提示；网络恢复和手机重启后的可达性受 Android 厂商后台限制。除非系统允许 ADB 重新开启，否则无法保证重启后完全无人操作。
- 两台手机首次配对须本人双方确认，观看须明确授权、可停止、可撤销。不得让扫码配对自动等同于无限期隐蔽观看许可。
- 只读视频：**不能**将未过滤的 ADB TCP/socket 原样通过公网中转，也不能开放 ADB shell/按键/触控/控制命令。

## 实际源代码核对

- `app/src/main/java/org/client/scrcpy/Scrcpy.java` 已通过 `Socket` 和 `DataInputStream` 获取 16 字节分辨率握手，随后读取 4 字节大端包长 + `MediaPacket`，使用 `VideoDecoder` 解码 H.264/H.265。
- `MediaPacket.Type`：AUDIO = 0、**VIDEO = 1**、CONTROL = 2、COMMAND = 3。`VideoPacket` 使用 10 字节媒体包头（视频标志 + 时间戳）。不得把 CONTROL/COMMAND 透传给观看端。
- 旧版 `OneTapConnection` 通过 ADB 到目标手机的 IP/端口再建立 `127.0.0.1:7008` 视频通道。异地版不能简单替换 IP 为日本服务器，因为这相当于跨互联网暴露整个 ADB 连接权限。
- `ScrcpyRelayPacketPolicy.java` 已增加媒体边界：只批准完整的视频包及合理的分辨率头；拒绝音频/控制/命令/未知大包。相关 JUnit 已加入。**目前还没有绑定到实际采集/传输线程**。
- `remote/relay_v1/server.py` 目前只提供经过设备令牌验证的配对、在线状态、双向信令。**还不传视频**。

## 预计完成的实际链路

1. 两端扫码并核对配对码，服务器将设备ID绑定到同一组；服务器拒绝不同客户组相互通信。
2. 用户 A 发起观看 B：服务器路由一次观看请求，B 必须处于本人已许可的接收状态，或者明确确认本次会话。
3. **B 本机**在 Android 系统允许的 ADB 环境中启动本机 scrcpy 编码服务；本机仅提取编码视频及必要的解码配置，经验证和裁剪后打包成只读视频消息。
4. B 通过 `WSS`（HTTPS/TLS）**主动向服务器**发送视频帧；服务器检查当前组、会话授权、角色及速率限制，只向经批准的 A 转发媒体，不写文件、不保留历史屏幕、不中转 ADB。
5. A 通过自己发起的 WSS 连接接收视频消息，经 `ScrcpyRelayPacketPolicy` 检验后交给现有 `VideoDecoder`，不携带触控及键盘命令。
6. 反向观看采用同样链路（B 看 A），双方可以撤销授权；断网重连时必须重新验证两端设备 ID 和本次观看会话，不根据 IP、端口、SSID 或设备名猜测对方。

## 剩余开发与硬性验收

- **尚未接入** B 本地 ADB 采集桥、WSS 二进制媒体中转、Android 解码适配及远程启动/停止会话。
- 不能依赖原有前台 `WakeLanService`；此无 VPN 分支已禁用它。
- 当前不使用 FGS，只能做受系统调度的后台信令检查，无法承诺系统强杀/重启后“随时秒级接通”。WorkManager 最短 15 分钟，而且可能被延迟。
- 日本 VPS 上的 TLS 反向代理、服务器性能、转码延迟和视频带宽都未验证；原有 3X-UI/Reality/Beta3 服务不应该被安装脚本覆盖。
- 必须在小米、vivo、OPPO Android 14+ 真机，分别测试首次授权、同 Wi-Fi / 跨网络、飞行模式、重启、ADB 端口重分配、拒绝观看、解绑、各类系统后台限制。
- 不能去掉 Android 自身强制安全授权或系统状态标识。

## 明确区分测试状态

- 配对 API 通过 ≠ scrcpy 能从本机正常编码；
- 网络信令在线 ≠ 后台设备可随时唤醒；
- 成功编译视频包策略 ≠ 实际经过服务器传输了画面；
- 不使用 VPN ≠ 具有无需授权的永久屏幕捕获能力。
