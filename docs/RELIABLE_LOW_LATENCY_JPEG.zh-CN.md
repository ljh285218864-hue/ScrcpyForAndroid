# ScreenSync 稳定传输与低延迟修复

基线：通知专用分支 `feature/screensync-notifications-isolated`；不修改用户授权、正在共享通知与“停止共享”按钮。

## 客户端
- JPEG 长边限制由 1440 调整为 1200，保持文字可辨识的同时降低压缩、网络和解码负载。
- 截图的单调时钟间隔下限 320ms，且截图完成后延迟 280ms，适配**当前已部署服务器最高 4 JPEG 帧/秒**的规则；避免网络抖动时补帧突发造成 `jpeg_rate_limit`。
- 继续用低容量 WebSocket 队列限制旧帧堆积，拥堵时降低 JPEG 质量并跳过采集；信号恢复后逐步恢复画质。
- 修正编码失败时缩放 Bitmap 未被释放的风险；无障碍截图将硬件 Bitmap 释放放入 `finally`，避免内存泄漏。
- 接收端最多只保留一个等待渲染的 Bitmap 和一个等待解码的任务；新帧替换未绘制的旧帧。移除每帧无必要的 JPEG byte[] 再拷贝，减少频繁 GC 卡顿。
- 仍在原 60 秒已授权会话续接窗口内时，WSS 重试间隔上限为 4 秒，优先恢复同一会话，不创建新的授权。
- 全屏观看断线提示改为“正在续接”，不会错误地引导用户关闭正常恢复中的会话。

## 中转服务端（源代码变更，需要部署才生效）
- 视频安全配额保持：最多 90 总帧/秒、每秒最多 8MiB。
- 当同一个合法 JPEG 会话短时超过每秒 4 帧时：**丢弃超额 JPEG 帧而不是直接撤销本次共享**。这防止网络缓存突发使双方被意外踢出，同时仍会按严格高流量限制撤销滥用会话。
- 服务端仍只中转已配对、明确批准且有有效会话的 JPEG；不是新的截屏授权机制。
- 服务器实际运行版本是否已替换，需在 VPS 上单独核实；本次仅修改 GitHub 中转程序源码，不触碰 VPS 现有 3X-UI/VLESS/WireGuard。

## 仍然存在的物理限制
- 当前 JPEG 协议最高 4fps，不能达到常规视频的 20–30fps 流畅度；长时间系统后台休眠、用户强行停止、无障碍失效、关闭唯一共享状态通知或断网超过恢复窗口仍可能结束共享。
- 想达到更高 FPS，需要双方升级与中转服务配合的视频编码方案（例如 H.264），并验证手机硬件、隐私授权和网络负载。
